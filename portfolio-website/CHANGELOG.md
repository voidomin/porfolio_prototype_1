- [x] Trackpad two-finger scroll getting stuck/locked up — reported directly (scrolling via a laptop trackpad's two-finger gesture would freeze, while keyboard arrows and mobile touch both worked fine). Root-caused by reproducing it: a realistic high-frequency wheel-event storm (matching real trackpad momentum-scroll cadence, not discrete mouse-wheel clicks) plus direct inspection of Lenis's live instance showed its internal model (`targetScroll`, `animatedScroll`, `velocity`) advancing completely normally while `window.scrollY` — the actual visible page position — stayed at exactly 0 the whole time. Cause: `globals.css` had `html { scroll-behavior: smooth }`, and Lenis writes `scrollTop` directly on that element every animation frame (~60/sec); each write restarted the browser's own native smooth-scroll animation before the previous one could progress, so sustained high-frequency input left the page barely moving even though Lenis's JS-side math was correct. Explains all three symptoms at once: keyboard arrows are native and not Lenis-driven at all, and touch scrolling bypasses Lenis entirely (`syncTouch` is off) — only sustained wheel input goes through the affected per-frame writes. Fixed by setting `scroll-behavior: auto`; verified safe since the only other native-scroll fallback in the codebase (`scrollTo()`'s fallback in `src/lib/lenis.ts`) already passes `behavior:"smooth"` explicitly as a JS API option, which overrides this CSS property regardless of its value. Confirmed with the same reproduction: `scrollY` went from stuck around 100px (out of ~3600px of nominal wheel input) to correctly reaching ~3300px, consistently across multiple runs, with anchor-jump navigation re-confirmed still smooth afterward.
- [x] Follow-up CLS investigation — the same production trace, re-run after the fixes above, still showed an identical CLS score, pointing at something the first pass hadn't touched. Root cause: `NatureScene.tsx`'s mountain-layer/cloud/sun/moon elements all size or position themselves as a percentage of their parent (a `position: fixed` container), and mounting the Hero's WebGL canvas measurably corrupts that parent's resolved dimensions for one frame before it self-corrects — confirmed with a clean, unconfounded test (mobile viewport, where `HeroScene` never mounts and nothing else changes): shift count there is exactly zero, reproducible every time on desktop. Timing fixes (deferring the mount via `requestIdleCallback`, reducing the canvas's own cost) didn't move the score at all — switching every percentage-based size/position in `NatureScene.tsx` to viewport units (`vh`/`vw`) did, taking the score from 0.48 down to 0.45 and the impacted-element count from 5 down to 1. One element (the back mountain layer) still shows a smaller residual that looks like a deeper rendering-pipeline interaction — noted honestly rather than claimed fully fixed. Kept as net-positive regardless: `HeroScene`'s `dpr` is now fixed at 1 (not `[1, 1.5]`) and `antialias` is off (confirmed visually unchanged via screenshot — the scene is flat-shaded and fog-blended, doesn't need MSAA/supersampling), and its first mount now waits for `requestIdleCallback` (capped at 1s). Full-page scroll perf after this pass: average frame time down to 19.63ms, worst-case frame down to 44.60ms.
